# 2026-10-17-02-vite-plus.md

**All the way in with Vite Plus: it decides what runs, in what order, and what is skipped; our code only does the
jobs Vite Plus has no tool for.**

Owner, 2026-10-17: "It's clearly the way to go"; "it's right, not you and me… adjust our stuff"; "we're going all
the way in with Vite Plus"; "do the complete renaming first… that tells you already the mapping between VP and your

and `node_modules/vite-plus/docs`. Read those before changing how anything is built, checked or run.

## Rules

- Vite Plus runs our tools; nothing of ours runs `vp run`. (The trial had Vite Plus calling the command line and
  the command line calling Vite Plus back: that is what broke.)
- A task runs one tool directly, visibly: no download, install, gate, second build or change detection hidden
  inside it.
- Checks never write. Fixing is `vp run fix`.
- Vite Plus's words for what Vite Plus does; ours only for what is ours. One name per thing everywhere.

## Steps

Done, each proven here (`vp run ci` whole: 247 browser checks in every language, 5 audits, a new app's 46):

1. The names, everywhere.
2. The task list once, in the package: `remyApp()` carries the tasks and one style; `remyDocs()` the docs' tasks.
3. The plain-function checks on `vp test`; Playwright only for the browser.
4. The project's own checks are one plain tool, `remy-check` (verifies; `--write` fixes, which `vp run fix` runs).
5. The browser path as tasks: `browsers`, `test:browser`, `test:audits`, `new-app`; `ci` runs them in turn.
6. The flow as scripts: `land` and `release` prepare, run `vp run ci`, then their own part; `setup` then `vp run ready`.
7. Hooks through Vite Plus (`vp config`, `vp staged` before a commit, `vp run ci` before a push); npm pinned.
8. Deleted what Vite Plus replaced: the check sequence, `ci.ts`, `unchanged.ts`, `dev.ts`, the local-build test
   helpers; the gate keeps only what costs money or ships (translation, Core Web Vitals).
9. What the tasks found the command line had hidden: the origins (the build reads `remy.config.ts` itself), the
   commit in the build's stamp (an input now), the proxy a cached task needs to download (untracked).

10. The workspace layout: `apps/remy-auth`, `apps/remy-auth-docs`, `packages/*` (`template/` and `fixtures/` stay at the
    root); the task list in two scopes (`remyApp()` the app's, `remyWorkspace()` the root's, with the app's tasks
    by their own names); the commands find the app by `wrangler.jsonc` and the docs by `docs.config.ts`.
11. GitHub: `setup-vp`, Vite Plus's task cache, `vp run <task>` per job.
12. Apps: `remy upgrade` writes the flow's scripts and the hooks from `tasks.js` (the one source the template and
    remy-auth are tested against) and names Cloudflare's build command.
13. Cloudflare: the branches' trigger at root `apps/remy-auth`, `npx vp run build`; the `vite-plus`
    branch built and published there, and our 238 checks passed against its preview.
14. Found on the way: `remy test` and `remy docs test` looked for Playwright's configuration at the root; `cli/`

15. An independent review (18 findings), each fixed and proven here: the docs translation check found no site

## Status

- **pnpm, a decision of its own:** `vp create`'s default, with a catalog. Its strict linking refuses what every app
  does now, importing `react`, `@tanstack/*`, `better-auth` and the rest through `@joeblew999/remy-ui` without
  listing them; adopting it means each app lists what it imports (or turning the strictness off, which leaves little
  reason to switch). It moves no file and no task, so it is a change to the platform's dependency design, not to
  this layout.
- The global `vp` in managed mode (Node from `.node-version`); every Claude cloud session sets it up itself
  (`.claude/settings.json`); `vp run ready` is Vite Plus tasks, ~50 s from nothing, ~4 s from the cache.
- A new app's first `generate` is never cached: Paraglide writes its project's housekeeping (README.md, .gitignore,
  .meta.json, .lix/, the plugin cache) and rewrites `settings.json` unchanged, once per checkout; from the second
  run nothing outside `src/paraglide` changes and it is cached. Not excluded: `settings.json` is a real input.
- When this lands: Cloudflare's main trigger runs `npm run build` at the root, which this change removes; from the
  same moment it must be root `apps/remy-auth`, `npx vp run build`, as the branches' is.
- **Owner's decision, open:** every new branch gets a Worker Preview of its own on Cloudflare (Workers Builds'
  previews, one per branch, each with build settings of its own), and a new one starts with old defaults: `npm run
  build` at the repository root, which this layout has no script for, so its check goes red until its settings are
  fixed (2026-10-17: the `vite-plus` and `leaves` branches; fixed for each through the API, `PATCH
  /builds/workers/<tag>/previews/<id>` with root `/apps/remy-auth`, `npx vp run build`, NODE_VERSION). The cause,
  found 2026-10-17: the Worker's build configuration holds both the legacy branch trigger (`branches: preview`,
  already right) and `previews_base_config`, which every new Preview copies and which still says `npm run build` at
  `/`. Cloudflare refuses to change that base while the legacy trigger exists (error 12048) and accepts a partial
  change of it as a success while keeping the old value. The fix is one call, `POST
  /builds/workers/<tag>/migrate_to_previews`: the legacy trigger's settings become the base and the trigger is
  removed. It has no undo, so it is the owner's. Until then a landing whose branch is new fails on that check, and
  the fix is the PATCH above, then a rebuild.
- Cloudflare installs with its own npm 10.9.2, not the pinned 11.19.1: Workers Builds honours no npm pin
  (`NPM_VERSION` tried and ignored, 2026-10-17). `npm ci` installs the lockfile exactly or fails, so it is left so.
